## 1. 当前目标

知识库入库阶段不仅解析 Markdown/PDF/TXT 的纯文本，还要把 Markdown 中图片里的有效信息提取出来，最终进入 Chunk → BGE-M3 + BM25 → Milvus。

目标链路：

```text
Markdown / PDF / TXT
        ↓
Parser Registry
        ↓
Markdown 图片识别
├─ ![alt](path)
└─ <img src="..." alt="...">
        ↓
图片解析
├─ 普通截图/文档图片 → OCR / 文本 / 表格 / 公式
└─ 流程图/架构图     → 语义描述 + 节点 + 可靠关系
        ↓
回填 Markdown
        ↓
Chunk
        ↓
BGE-M3 Dense + BM25
        ↓
Milvus
```

当前真正卡住的问题不是普通 OCR，而是：

> **流程图/架构图中的节点关系、箭头方向、分支条件恢复不稳定。**

## 4. Markdown 图片解析：已完成部分

核心文件：

```text
backend/core/parsers/markdown_images.py
```

当前支持：

- `![alt](path)` 标准 Markdown 图片
- `<img src="..." alt="...">` HTML 图片（Obsidian 里实际存在）
- 本地相对路径
- Windows 绝对路径
- HTTP / HTTPS 网络图片
- 网络图片最大 20 MB
- 最多 3 次重定向
- 拒绝 localhost / 私网地址，避免 SSRF
- 同一图片重复引用只解析一次
- 图片解析失败不会阻断整篇 Markdown 入库
- 原图片引用继续保留
- 图片提取内容插在原图片后方
- MinerU 只返回图片路径时判定为 low-value
- 明显错误 Mermaid（大量 `Node 1/Node 2/...`）会被删除

回填格式：

```markdown
![项目流程](img/项目流程.jpg)

[图片内容：项目流程]
...提取出的有效文本...
[/图片内容]
```

这样后续 Markdown Heading Chunking 会自然把图片语义与相邻章节一起切分。

最典型测试图：

```text
E:\obsidian notes\05_EduRAG 项目\03-笔记\img\image-20260305101549208.png
```

```text

bge-m3

...
```

但是 MinerU 会先把整图拆成大量：

```text

image block
...
```

对应：

```text
data/mineru/_flowchart_prompt_test/rag_flow/structured_content.json
```

因此全局关系容易丢失：

```text

条件分支             ❌ / 不稳定
```

结论：

> **MinerU 的问题不是看不到字，而是“先切块再理解”导致流程图的全局连接关系丢失。**

## 9. 已做的 MinerU 流程图优化

### 9.1 advanced 图片 Prompt 增强

文件：

```text
scripts/mineru_parse_worker.py
```

针对 advanced 图片，在独立 worker 进程中扩展 MinerU 的 `DEFAULT_PROMPTS["image"]` / `["chart"]`，要求：

- 保留真实节点文字
- 保留箭头方向
- 保留 Yes/No 等条件
- 禁止 `Node 1 / Node 2 / Step 1`
- 看不清的边宁可不输出，也不要猜

**没有修改 site-packages，只修改当前 worker 进程里的默认 prompt。**

真实重跑结果：

- 不再大量产生 `Node 1 → Node 2`
- 但主要退化成 OCR 文本
- 仍不能可靠恢复整张图关系

结论：

> **继续堆 MinerU prompt 收益有限，无法根治关系恢复问题。**

### 9.2 错误 Mermaid 过滤

文件：


```text

```

认为该 Mermaid 不可信，直接丢弃。

原则：

> 宁可保留可靠 OCR，也不要把错误关系写入 Milvus。

## 13. 建议的最终架构

不建议继续让 MinerU 单独承担所有图片语义理解。

建议：

```text
Markdown 图片
        ↓
路径解析 / 下载 / 去重
        ↓
┌──────────────────────────┐
│ MinerU                   │
│ OCR / 文本 / 表格 / 公式  │
└──────────┬───────────────┘
           │
           ├─ 普通图片
           │    ↓
           │  直接作为 RAG 文本
           │
           └─ 疑似流程图/架构图
                ↓
         Qwen3.5:4b 整图理解
                ↓
       description + nodes + edges
                ↓
           质量门控
                ↓
           回填 Markdown
```

最重要原则：

> **RAG 的目标不是完美重建 Mermaid，而是让图片里的真实信息可被检索和回答。**

建议优先级：

```text
可靠 description
    >
可靠 nodes
    >
可靠 edges
    >
完整 Mermaid
```

如果边不可信：

- 保留 description
- 保留 nodes
- 不写 edges
- 不强行生成 Mermaid

## 14. 下一步建议

### P0：不要继续重点调 MinerU Prompt

已经确认根因是：

```text
整图 → block 拆分 → 全局关系丢失
```

继续调 MinerU prompt 收益有限。

### P1：完善 Ollama VLM 质量门控

建议给 `ollama_image_understanding_worker.py` 增加：

1. 只对 `flowchart / architecture / pipeline` 做第二阶段。
2. source/target 必须存在于 nodes。
3. 禁止 self-loop。
4. 禁止 `Node 1/Node 2` 占位。
5. 边过少或明显可疑时，不生成 Mermaid。
6. edge 作为可选增强，不要作为必须信息。
7. 最终输出以 RAG 友好的自然文本为主。

推荐最终文本：

```text
[图片内容：RAG流程图]

图片类型：流程图

整体描述：
该图展示 RAG 的检索、增强和生成流程。

主要节点：
- Query
- Embedding
- Vector database
- Context
- Prompt
- LLM
- Response

明确关系：
- Query → Embedding
- Embedding → Vector database
- Vector database → Context

[/图片内容]
```

这种格式比只存 Mermaid 更适合 BGE-M3 + BM25。

### P2：做独立接口，再接 MarkdownImageResolver

不要把 Ollama HTTP 逻辑硬塞进 `MarkdownImageResolver`。

建议抽象：

```python
class ImageSemanticAnalyzer:
    def analyze(image_path) -> ImageSemanticResult:
        ...
```

结果包含：

```text
type
description
nodes
edges
quality flags
```

然后：

```text
MinerU OCR
+
可选 Qwen VLM
↓
merge
↓
_format_enrichment()
```

### P3：性能优化

真实参考：

```text
MinerU advanced 单张复杂流程图  ≈ 211 秒
Qwen3.5:4b thinking            ≈ 211 秒
Qwen3.5:4b think=false 单轮    ≈ 10.4 秒
Qwen3.5:4b 两阶段 fast         ≈ 134.9 秒（仍需优化）
```

建议：

- 按图片内容 SHA256 做持久缓存，不要只按路径
- 同一图片绝不重复跑 VLM
- 只对复杂图触发第二轮
- 普通图片尽量走 MinerU basic/OCR
- 后续可考虑把 Markdown 图片默认从 `advanced` 调回轻量 OCR，再由复杂图单独走 Qwen VLM
- 该链路只用于离线入库，**绝对不要放到在线 QA 请求里**
